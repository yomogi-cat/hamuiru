# 見守りシグナルを本人の生活スタイルから選ぶ設計

- 日付: 2026-07-25
- 対象: `README.md` / `docs/architecture.md` / `src/config.gs` / `src/jobs.gs`

## 背景と課題

初期実装は「電気ポット」を見守りシグナルとして固定していた。判定は当日0:00〜10:00に
`power_w >= 500W` の記録が1件もなければアラート、という形である。

この前提には2つの弱点がある。

1. **生活スタイルへの非依存性がない**
   ポットを毎日使う人もいれば、使わない人もいる。同じ人でも夏は麦茶に切り替えて使わなくなる。
   使わない日にアラートが鳴れば、家族は数週間で通知を読み飛ばすようになり、本命のアラートが埋もれる。
2. **短時間稼働家電はポーリングで取りこぼす**
   電気ポットの沸騰は5分程度。30分ごとのポーリングが沸騰中に当たる確率は1〜2割しかない。
   元気にお茶を淹れていても誤アラートが出る構造だった。

実際の運用対象（祖母）は**テレビを毎日必ずつける**。テレビは数時間連続で稼働するため、
30分ポーリングでも確実に捕まる。つまり家電を選び替えるだけで、原理的な確実性が上がる。

## 設計方針

**このシステムの精度は、コードよりも「どの家電を見るか」でほぼ決まる。**
したがって家電選定を README の第一級の設計原則として明文化し、
コード側は家電を差し替えられる構造にする。

判定ロジック自体（積算値ベースの判定など）は今回のスコープ外とし、
本方式で取りこぼす家電タイプは「向かない」と正直に書いて回避策を示す。

## 変更内容

### 1. シグナル選定の原則を明文化（README）

設計思想に3本目の柱として「シグナルは本人の生活から選ぶ」を新設する。選定条件は3つ。

1. 毎日必ず使う
2. 季節や天候に左右されない
3. 使わないこと自体が異常のサインになる

向かない家電とその理由も明記する。

| 家電 | 向かない理由 |
|---|---|
| 冷蔵庫 | 24時間通電しているため、生活のシグナルにならない |
| エアコン・こたつ・扇風機 | 季節依存。使わない時期は判定が成立しない |
| 照明 | 日照時間で点灯タイミングが変わる |
| 電気ポット | 夏に使わなくなる。稼働が短くポーリングで取りこぼす |

### 2. 家電タイプ別の判定設計（README）

| タイプ | 例 | しきい値の決め方 | 30分間隔での適性 |
|---|---|---|---|
| 長時間・中電力 | テレビ | 待機電力と使用時電力の中間（待機0.5W / 使用60W → 20W） | 推奨 |
| 短時間・高電力 | 電気ポット、電子レンジ | 稼働時の電力より低く（500W） | 非推奨。使うならトリガー間隔を10分に詰める |

### 3. 「観察期間」をセットアップ手順に格上げ（README）

「生活スタイルに合わせる」を精神論にせず、手順として定義する。

1. プラグを設置し、`collectPower` のトリガーだけ登録する（この段階では通知させない）
2. 1〜2週間ログを溜める
3. `log` シートから3つの値を読み取って決める
   - 使用時と待機時の `power_w` → `POWER_THRESHOLD`
   - 最も遅かった日の初回使用時刻 → `morningCheck` の判定時刻（+1時間の余裕を持たせる）
   - 「1日も使わなかった日」があるか → あればその家電はシグナルとして不適格。選び直す
4. `morningCheck` / `weeklySummary` のトリガーを登録して本運用開始

STEP 3 の3点目が重要で、**観察期間は家電選定そのものの検証も兼ねる**。

判定時刻は README 上で断定せず、10時を初期値として提示し、観察期間の結果で調整する手順とする。

### 4. コード変更

**`src/config.gs`**

- `APPLIANCE_NAME` を任意プロパティとして追加（省略時 `'家電'`）。通知文の家電名に使う
- `POWER_THRESHOLD` をデフォルト値ありから**必須プロパティに昇格**する
  - 理由: 観察期間で実測して決めるべき値にデフォルトがあると「決めなくてよい」と誤読される。
    未設定なら `validateConfig_()` が明示的に落ちるほうが、静かに誤ったしきい値で
    動き続けるより安全である
- 数値として不正（非数・0以下）な場合も例外にする

**`src/jobs.gs`**

- 通知文の「電気ポット」を `config.applianceName` に置換（`morningCheck` / `weeklySummary`）
- 見守りアラート文の「（0:00〜10:00）」を実行時刻から生成する。判定時刻がトリガー設定で
  変わるようになったため、固定文言だと嘘になる

**`docs/architecture.md`**

- 定期ジョブ表・シーケンス図の文言を家電非依存に一般化
- セットアップ順序に観察期間を反映

## 検討したが採用しなかった案

- **積算値（`electricityOfDay`）ベースの判定**
  短時間・高電力家電の取りこぼしを根本解決できるが、`electricityOfDay` は SwitchBot の
  ドキュメント上「当日の使用時間（分）」とされており、現在のログ列名 `daily_kwh` と
  意味が食い違っている可能性がある。実機での確認が必要なため今回は見送り、
  README に制約として明記する方針とした。
- **最終活動からの経過時間で判定するローリング方式**
  固定時刻判定より発見の空白が縮まるが、今回の課題は「時刻の調整」ではなく
  「シグナルの選定」であるため対象外とした。
- **複数センサーのOR判定（人感センサー + Hub の追加）**
  確実性は最も高いが、追加ハードウェアと訪問設置が必要。将来の拡張候補として保留。

## 残るリスク

- テレビに切り替えても「テレビをつけたまま倒れる」ケースは検知できない。これは
  デッドマンスイッチ方式の原理的な限界であり、複数シグナル化以外の解決策はない
- `POWER_THRESHOLD` の必須化により、未設定の既存デプロイはジョブが例外で停止する。
  本運用開始前のため実害はないが、README のプロパティ表で必須であることを明示する
